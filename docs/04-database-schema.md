# 4. Database Schema

CampusVibe uses a single SQLite database file at `data/campusvibe.db`,
created automatically on first run. The schema is defined entirely in
`server.js` as a block of `CREATE TABLE IF NOT EXISTS` statements, plus a
handful of additive `ALTER TABLE` migrations run on every startup (see
[03-architecture.md](./03-architecture.md) for why). There are **7
tables**; two of them (`waitlist` and `notifications`) exist in the
schema but currently have **no code path that reads or writes them** —
see the note at the end of this document.

## Entity relationship summary

```
users ──< events ──< discounts
  │          │
  │          ├──< tickets ──< attendance
  │          │        │
  │          └──< waitlist (unused)
  │
  └──< tickets, attendance, notifications (unused)
```

- One **user** can create many **events** (if they're an organizer).
- One **event** has many **tickets**, **discounts**, and **attendance**
  records.
- One **ticket** belongs to one user and one event, and can have
  **attendance** records (usually one, from check-in).

## `users`

Every person who has ever registered — students, organizers, and the
admin — lives in this one table; the `role` column distinguishes them.

| `name` | TEXT | |

| `password_hash` | TEXT | `bcrypt` hash. **Null for Google-only accounts** — see [06-authentication-and-roles.md](./06-authentication-and-roles.md) |
| `mobile` | TEXT | |
| `roll_number` | TEXT | Student ID / roll number |

### Event ID format

Unlike every other UUID column in this schema, an event's `uuid` is
**not** a random UUID. It's generated by `generateEventUuid()` in
`server.js` as `DDMMYYYY` (the creation date) followed by 6 random
digits — e.g. an event created on 8 July 2026 might get
`08072026482913`. This is a deliberate UX choice: it produces a
human-typeable, human-rememberable ID that an organizer can read aloud or
write on a whiteboard, which matters because this same ID is what a
volunteer at the door types into the manual attendance check-in tool. A
collision-retry loop (`createUniqueEventUuid`, up to 5 attempts) handles
the very unlikely case of two events generating the same ID on the same
day.

## `discounts`

Organizer-configured discount codes, scoped to one event each.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER, PK, autoincrement | |
| `code` | TEXT, unique, not null | Stored and matched in uppercase |
| `event_id` | INTEGER, not null | FK → `events.id` |
| `percentage` | INTEGER | e.g. `20` for 20% off. Mutually used with `amount_cents` (a code typically sets one or the other) |
| `amount_cents` | INTEGER | Fixed-amount discount, in the smallest currency unit |
| `max_uses` | INTEGER | `NULL` means unlimited |
| `used_count` | INTEGER, not null, default `0` | Incremented each time the code is successfully applied |
| `active` | INTEGER, not null, default `1` | Boolean |
| `created_at` | TEXT, not null | |

Note the **unique constraint is on `code` alone**, not on
`(code, event_id)` — meaning discount codes are unique *across the whole
platform*, not just within one event. Two different organizers can't both
create a code called `WELCOME10`.

This table is created by the schema but **no route in `server.js` ever
inserts into or selects from it.** There is no "join waitlist" endpoint

### Payment status state machine

`payment_status` moves through these values:

```
                 ┌─────────────────────────────────────┐
                 │                                       │
 registered ──▶ unpaid ──(proof submitted)──▶ pending ──┼──▶ paid  (approved — QR generated)
   (free)  │                                             │
    │       └──(5 min pass, no proof)──▶ expired         └──▶ rejected ──(resubmit proof)──▶ pending
    │
    └──(price = 0)──▶ paid  (immediately, no payment step at all)
```

- **`unpaid`** — a seat is held, but no proof has been submitted yet.
  This is the *only* status subject to automatic expiry (see
  [08-core-features.md](./08-core-features.md) for the 5-minute hold
  system).
- **`pending`** — proof (a transaction ID) has been submitted; awaiting
  organizer review.
- **`paid`** — an organizer approved the proof. A QR code is generated at
  this exact transition (see `POST /api/organizer/payments/:ticketUuid/approve`
  in [05-api-reference.md](./05-api-reference.md)).
- **`rejected`** — an organizer rejected the proof, with a required
  reason. The student can resubmit proof, moving the ticket back to
  `pending`.
- **`expired`** — the 5-minute unpaid hold lapsed with no proof
  submitted. The seat is released back into the event's available
  capacity.
- **`verified`** — referenced in a couple of capacity-check queries
  alongside `paid`, but no code path actually sets a ticket to
  `verified` — in this codebase, `paid` is the only "confirmed" state
  that's ever written. Likely a naming holdover from an earlier version.

## `attendance`

A log of check-in events. Note this is a **log**, not just a flag — a
new row is inserted on every check-in action, while the "is this person
currently checked in" flag actually lives on `tickets.checked_in`.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER, PK, autoincrement | |
| `event_id` | INTEGER, not null | FK → `events.id` |
| `user_id` | INTEGER, not null | FK → `users.id` |
| `ticket_id` | INTEGER | FK → `tickets.id`. **Nullable, and left `NULL` by the manual-by-ticket check-in path** — see [11-known-limitations-and-tech-debt.md](./11-known-limitations-and-tech-debt.md) |
| `present` | INTEGER, not null, default `0` | Boolean |
| `timestamp` | TEXT, not null | |
| `source` | TEXT, not null | `'qr'` or `'manual'` |

## Migrations applied at every startup

These run unconditionally on every server start, wrapped so a "duplicate
column" error (meaning the migration already applied in a previous run)
is silently ignored:

```sql
ALTER TABLE users  ADD COLUMN organizer_status TEXT;
ALTER TABLE users  ADD COLUMN organizer_reason TEXT;
ALTER TABLE users  ADD COLUMN avatar_url TEXT;
ALTER TABLE events ADD COLUMN discounts_enabled INTEGER NOT NULL DEFAULT 0;
ALTER TABLE tickets ADD COLUMN hold_expires_at TEXT;
```

If you're adding a new column to this schema, follow the same pattern:
add an `ALTER TABLE` line here (in `server.js`) rather than editing the
original `CREATE TABLE` statement, so existing databases pick up the
change without a manual migration step.
